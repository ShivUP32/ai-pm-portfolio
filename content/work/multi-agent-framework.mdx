## Overview

A reusable framework that lets us spin up new conversational agents in two weeks instead of six. Three agents — Support, English Teacher, and Doubt Solver — now share one orchestration layer, one memory system, one tool registry, and one analytics pipeline. Each one keeps its own persona, knowledge, and tool catalog.

## Context

We were running three conversational AI products in parallel:
* A **Support Agent** answering customer queries and integrating with our ticketing system.
* An **English Teacher** giving learners real-time conversational practice with corrections.
* A **Doubt Solver** helping students work through academic problems step-by-step.

Each one started its life as a separate project with a different team, timeline, and codebase. By the time we had three in production, we were maintaining three nearly-identical stacks — and the cost of adding a fourth agent was the same as building the first.

## The Problem

The duplication was eating the team alive:
* **Six weeks** to launch every new agent. Most of that was rebuilding the same plumbing: NLU, dialog management, memory, tool integration, and analytics.
* **N&times; engineering effort** for every fix. A bug in conversation memory had to be patched and verified in three separate places.
* **Inconsistent UX**. The Support Agent handled agent handoffs differently from the Doubt Solver. The English Teacher remembered user preferences, while the others did not.
* **Improvements stranded**. A better intent classifier shipped to one agent never reached the other two.

The deeper issue was strategic. If we couldn't ship new agents quickly, we couldn't test new product ideas. Every agent concept was a six-week engineering commitment before we knew if it would resonate.

## Goals

1. **Velocity**: Cut new-agent integration time from six weeks to two weeks.
2. **Efficiency**: Share improvements automatically across all agents.
3. **Fidelity**: Keep each agent's unique persona, knowledge, and tools intact.
4. **Ownership**: Make the framework owned by one platform team, with agent personas owned by individual product squads.

## Approach

I led the design of a layered framework. The work started with a component audit: I mapped every component across the three agents and labeled each as either *shared* (the same across all) or *specific* (the thing that makes the agent feel different).

The split that emerged:

### Shared Core (~70% of every agent)
* **Conversation Engine**: NLU, dialog manager, response generator.
* **Memory & Context**: Session state, long-term memory, vector store for RAG.
* **Tool Registry & Selector**: Function calling and ReAct loop.
* **Channel Adapters**: Web, app, voice, and WhatsApp integrations.
* **Safety & Guardrails**: PII filtering, moderation, and audits.
* **Analytics & Observability**: Logs, metrics, and conversation replay.
* **Orchestrator**: Core agent lifecycle and persona loader.

### Per-Agent Persona Layer (~30%)
* **System Prompts**: Prompt templates and behavior rules.
* **Tool Catalog**: Which tools this specific agent is authorized to call.
* **Knowledge Bindings**: RAG sources specific to this agent.
* **Configuration**: Tone, style, and escalation/human-handoff rules.

The architectural rule we held to: **Shared is reusable; per-agent is what makes the agent feel different.** Anything else got pushed down into the core.

## Solution

The framework runs as a central service. Each agent is configured declaratively—a persona file specifies the prompts, tools, knowledge sources, and behavior rules. The orchestrator loads this configuration at runtime and routes the conversation through the shared core.

Key design choices:
* **Central Tool Registry**: Tools are registered centrally, not embedded in agent code. Adding a new tool means writing it once and exposing it to whichever agents need it.
* **Namespaced Memory**: Memory is namespaced per user and per agent, so the English Teacher doesn't accidentally see a user's support tickets.
* **Shared Evaluation Harness**: Every agent gets regression tests, quality scoring, and A/B testing infrastructure out of the box.
* **Hot-Reloadable Personas**: Product teams iterate on prompts and tool catalogs without touching framework code or redeploying the core service.

## The Three Agents on the Framework

* **Support Agent**: Resolves customer issues end-to-end. Integrates with ticketing, order, and refund APIs. Escalates to human agents when needed. Tone is calm and action-oriented.
* **English Teacher**: Conversational language practice with real-time grammar and pronunciation feedback. Tracks learner progress. Tone is patient, encouraging, and playful—corrections happen without breaking conversational flow.
* **Doubt Solver**: Step-by-step academic problem-solving. Retrieves from subject-specific knowledge bases. Generates worked examples and practice problems. Tone is methodical—it deliberately doesn't hand over the final answer too quickly.

The transition to a unified framework dramatically improved our delivery speed and system stability.

### Qualitative Wins
* **Unified Ownership**: A single engineering team now owns and maintains the core orchestrator, freeing product squads to focus purely on user experience and prompt tuning.
* **Instant Improvements**: Any optimization made to the core conversation engine or NLU automatically upgrades all three agents.
* **Seamless Context Passing**: Users can be handed off across agents (e.g., a Support conversation can pass relevant user context to the Doubt Solver) without losing history.

## Intellectual Honesty: What I Learned

* **The Persona/Core split is harder than it looks**. We rewrote the boundaries three times before they felt right. The temptation is always to push more into the core "for consistency," but that kills the customization that makes each agent uniquely useful.
* **Evaluation is the framework's superpower**. Once every agent ran through the same evaluation harness, quality conversations became data-driven instead of opinion-driven.
* **Get the tool registry right early**. Poor tool descriptions cause the LLM to select the wrong tools. Treating each tool as a small product—with its own spec, owner, and regression tests—paid off immediately.
* **Don't unify what isn't actually duplicated**. We almost unified the knowledge bases across agents. We didn't, and that was the right call—each agent's knowledge domain is genuinely different, even if the retrieval mechanism is identical.
